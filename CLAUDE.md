### The matrix — what `prototype` actually changes (adopted 2026-09-25, closes DEBT-55)

`/qa` reads this table. It is expressed as *what changes per path*, because a project-wide profile
that flattens this product's own verdict path to the same rigor as a docstring is the wrong shape
for a product whose entire value is being a gate.

| Path | `prototype` | `standard` | Never profile-driven |
|---|---|---|---|
| **Verdict path** — `classifier/gate.py` (`overall_gate`), `platform/scoring.py` (`build_score_inputs`'s gate value) | **runs at `full` anyway** — fresh-instance stamp with a mutation matrix, never a `re-gate skipped` | same | — |
| **Wire-contract path** — `adapter/` code whose correctness depends on an external API's shape | **SR-1 binds** (`REGRESSIONS.md`): verified against a recorded live response, never against a fixture authored from the parser | same | — |
| **Any fix round touching `src/`** | **never qualifies for `re-gate skipped`, at any profile** | same | — |
| Reviewer passes on **docs/tests-only** deltas | **one pass** | two | — |
| Mechanical floor — tests exist and pass, mypy strict, ruff, secret scan | — | — | **always** |
| `Risk: high` spec → `/test` stamp · DEBT-44 instance independence · NFR-01 per-UC `Containment`/`Observability` markers | — | — | **always** — read from the **SPEC header** and the NFR file, **not** from this profile |

**So `prototype` buys exactly one thing: one reviewer pass instead of two on docs- and tests-only
deltas.** Anything that edits `src/` is unaffected. Rows 1–3 are the two auditor overrides plus
**SR-1**, which a PIN established in practice: a defect class can outrank the profile, and when it
does the override is written here rather than re-argued per incident.

**Every gate this profile turns off must be RECORDED** — `skipped: prototype profile`, in the QA
report **and** the state log. That invariant is what this matrix makes mechanically checkable; it
was unenforceable for the four days the profile existed without one.

⚠️ **Known gap, filed 2026-09-25:** `docs/specs/SPEC-01-baseline-regression.md` is the **only**
spec in the repo. Epic E (the local console) has none — so the last row's `Risk: high` lookup has
no SPEC header to read on the one surface that spends IDP quota from an unauthenticated loopback
port. That is a gate with nothing to read, not a gate this profile lightened.

> **Changed 2026-09-21 by user decision: `standard` → `prototype`, to reach the MVP faster.**
>
> Previous rationale, preserved because it weighed this exact argument and reached the opposite
> conclusion: *"this is a real, long-lived internal product, but the first milestone is an MVP.
> Start `standard`; run individual gates at `--rigor=full` before the tool is trusted to gate
> other teams' prompt changes."* The reversal is deliberate and is recorded, not silently applied.
>
> **What does NOT change — these are not profile-driven and still bind:**
> - **The mechanical floor holds in every profile:** tests exist and pass, static analysis clean,
>   secret scan. The classifier is pure and must always stay unit-tested.
> - **`Risk level: high` still requires a `/test` stamp.** `/qa`'s rigor gate reads the risk level
>   from the **SPEC header**, not from this profile, so SPEC-01 cannot be QA'd on an
>   `/implement`-only stamp regardless of what this line says. **Profile ≠ risk level.**
> - **NFR-01's markers are per-UC, not per-profile:** `Containment: REQUIRED` (HARDEN-01, five
>   conditions), `Observability: REQUIRED`. Lowering the profile does not waive them.
> - **DEBT-44** (a `/test` gate on a Risk:high delta may not be run by the APPROVE-issuing
>   reviewer instance) is a written project rule, not a profile setting.
>
> **What this buys, and what it costs.** Fewer reviewer passes and lighter gates per story, so
> stories close faster. The cost is a lighter *Done*, honestly labelled — and every gate this
> profile turns off must be **recorded** (`skipped: prototype profile`) in the QA report and the
> state log, never silently dropped.
>
> ⚠️ **The specific risk, stated once so it is on the record.** This product's entire value is
> being a CI gate other teams trust. On 2026-09-21 alone, the gates being lightened found two
> **fail-open** defects — `overall_gate` returning `"PASS"` for any unrecognised verdict, and a
> non-string `document_id` being written to the platform while the call returned success. Both
> would have produced **silently-wrong GREEN builds**, which is the worst failure this system can
> produce and the one a lighter profile is least likely to catch. Neither was found by a test
> suite; both were found by mutation testing and independent review.
>
> **Re-raise to `standard` before this tool gates another team's prompt changes**, and run the
> individual gates at `--rigor=full` before that point. Until then, treat green as "the MVP's own
> tests pass", not as "this gate can be trusted".

## Domain
- **Product:** IDP Regression Tester — a system that validates MuleSoft Anypoint IDP extraction output against a known-good reference, so a changed extraction prompt (or action version) can be judged better or worse with confidence.
- **Domain/URL:** internal tool — n/a
- **Personas:** Prompt Engineer (iterates extraction prompts and runs regressions), Golden Set Curator (non-engineer; maintains expected outputs through the platform UI), CI Pipeline (automated gate on prompt-change PRs).
- **Epics:** A IDP adapter · B Classifier & gate · C Golden-set management · D Run orchestration & platform integration · E Remediation UI · F Document-type routing & structural novelty
- **Compliance regime:** none formal — but extracted fields (invoices, IDs, totals) can contain financial data / PII. **Design rule: document files never enter the evaluation platform; only `document_id` and expected fields are stored.** **⚠️ REVERSED 2026-09-25 (user decision).** The platform now receives **as much information as possible** — *"[the platform] is the information point here"*. A run writes the expected/actual/confidence behind every verdict: score comments carry `expected … actual …`, the trace span carries a `detail` map per leaf, and the experiment item carries `expected_output`. The document FILE still never leaves the machine. PII is handled where it belongs — the IDP action can be configured not to parse it, plus a filter or a later deletion pass over the platform.

> The 2026-09-19 decision this replaces (DEBT-18 option B) kept every value off the platform so that a self-hosted instance could not become a second copy of the golden set. That reasoning is not wrong, it is outweighed: the tool is unusable as an *information point* if a red score cannot say what the value was. **What this costs, stated once:** the self-hosting obligations already recorded here (encryption at rest, DB access control, backup — ADR-0001/N25) stop being paperwork and become the control. `--platform-values verdicts-only` restores the old payload exactly, per run.

Treat golden-set contents as sensitive.
- **Sensitive surfaces:** golden-set storage (expected values), IDP credentials (OAuth client secret), evaluation-platform API keys.
- **Canonical source docs:** glob `docs/init/` (discover by role, not by filename).

| **BOTH HALVES — archive + two versions, one command** | `.venv/bin/python scripts/compare_versions.py (--zip <corpus.zip> \| --document-dir <dir>) --dataset <name> --org <id> --action <id> --trusted-version <v1> --candidate-version <v2> --yes` — pins every document at `--trusted-version`, then verifies every one of them at `--candidate-version`. **The archive is unpacked ONCE**, into its own `<store>/documents/<sha256[:16] of the archive>/` (never a directory shared with earlier corpora, which the pin half would also pay for), and both halves are pointed at that directory, so the bytes compared are provably the bytes pinned (two separate invocations each unpack their own copy with nothing checking they match). - **Pin-store layout — the paths ARE the relationship (user decision, 2026-09-25).** `<store>/goldens/<action-id>/<action-version>/<document>.json` (one golden per document, written as a one-entry golden set so it is exactly what `provision_golden_dataset.py --seed <document_id> --golden-file <that>` already validates), `_pins.json` beside it for the document directory and dataset, and `<store>/captures/<action-id>/<action-version>/<document>.raw.json` on the same axis — a raw response only means anything against the version that produced it. The same document can therefore be pinned at several versions without collision **on disk** — but **into a different dataset per version** (**user decision, 2026-09-27**): the platform item id is `uuid5(dataset|document_id)`, with no version, so two versions pinned into one dataset would be one platform item holding whichever was pinned last. `pin_document` refuses that before spending, and `verify_document` refuses a store already in that state (DEBT-89). A store holding goldens from more than one version says so in its own paths. `--action`/`--version` are validated against `^[A-Za-z0-9._-]{1,128}$` before they reach a path. `verify_document.py` selects a pin set by reading that tree: unambiguous with one (action, version), and with several it **refuses to guess** — name it with `--action` / `--trusted-version`. Provenance also travels to the platform: each dataset item carries `metadata: {trusted_action_id, trusted_action_version, pinned_at}`, which is run identity, not extracted content, so INV-01/DEBT-18 are untouched.
| **Pin validated file(s) to the trusted version** | `.venv/bin/python scripts/pin_document.py (--file <doc> \| --zip <corpus.zip> --all \| --document-dir <dir> --all) --dataset <name> --org <id> --action <id> --version <trusted-v> --yes` — **`--all` is required for `--zip`/`--document-dir`**: a batch spends one extraction per document and pointing at a folder never implies that. `--zip` unpacks flat into `--extract-to` (default `<store>/documents/`) with the same trust-boundary checks as the other batch tools, and that directory is what verification resolves against. Re-runnable: an already-pinned document is skipped, not re-paid for — **"already pinned" means the same bytes**: each pin records the document's sha256, and a same-named file with different content is refused before any spend (`--repin` re-reads it); `verify_document` refuses the same mismatch, and `bootstrap_golden_set --resume` refuses a capture taken from other bytes (DEBT-100) — so re-running after a failure retries only what failed (`--repin` to force). — reads the file once with the TRUSTED version and records that reading as the golden for that file: one dataset item, upserted on its deterministic id. Per document; **no corpus statistics, no sparsity rule** — **every** field is `critical`, including the ones the trusted version read as EMPTY, because verification uses the `pinned-file` classifier where empty-against-empty is agreement and invented content is a failure. Keeps the raw capture, and records the file's directory so `verify_document.py` can set `IDP_DOCUMENT_DIR` itself. Costs one extraction; `--repin` to re-read. |
| **Verify pinned file(s) against a NEW version** | `.venv/bin/python scripts/verify_document.py (--file <doc> \| --all) --dataset <name> --version <new-v> [--zip <corpus.zip> \| --document-dir <dir>] --yes` — by default the documents come from wherever they were when pinned; `--zip`/`--document-dir` takes them from a new source instead (a fresh checkout, another machine, the archive re-sent), unpacking to `<store>/verify-documents/` so the pin-time copies the goldens were read from are left alone. Written owner-only (`0700` directory / `0600` file) — an operator on a shared or multi-user host should still confirm that before trusting it as a narrower disclosure surface than the platform. It is the operator's to delete; nothing in this codebase prunes it automatically.
- **ZIP input (2026-09-25).** Both batch tools take `--zip <corpus.zip>` in place of `--document-dir` — a corpus arrives as an archive, not a mounted folder. It is unpacked **flat** into `--extract-to` (default `<out>.documents/` for the draft tool, `.idp-regression-noise-floor/documents/` for the noise floor), owner-only, and that directory is **what `IDP_DOCUMENT_DIR` must point at for the later `run_eval`** — the golden set names those files and nothing copies them again; the draft tool prints the absolute path in its closing summary. Flat because a `document_id` is resolved as one filename under `IDP_DOCUMENT_DIR`; two documents sharing a basename are disambiguated by folding in their folder (`jan__a.pdf`), never silently overwritten. Unpacking is treated as a **trust boundary**, not a convenience: path-traversal (zip-slip) entries and symlinks are refused and reported, `__MACOSX`/`.DS_Store`/AppleDouble junk is dropped silently, non-document entries are skipped with a note (a `.xlsx` would cost a real extraction), and the archive as a whole is refused past an entry-count, uncompressed-size or per-entry compression-ratio cap. `--plan` validates and counts the archive without writing a byte.
- **`--glob` now defaults to documents AND images** (`*.pdf,*.png,*.jpg,*.jpeg,*.tif,*.tiff,*.webp,*.bmp`, comma-separated) in both batch tools. A scanned-invoice corpus is usually TIFFs or JPEGs, and the old `*.pdf` default would have processed a handful of files out of a zip of thousands and reported success. Narrow it with `--glob '*.pdf'` when that is what you mean.
- **Per-file scenario (user decision 2026-09-25) — separate from watching an Action for new versions, which is unchanged.** "This file is already validated against the current Action version; I change the LLM and publish a new version; the file must still be valid." `pin_document.py` records the trusted version's reading of that one file as its golden; `verify_document.py` re-reads it with the new version through the ordinary gate. The golden is **per document** — nothing aggregates across files, and a field's presence in other documents is irrelevant to whether it is gated here. Values are compared, not just presence: canonicalized by `type`, so `1250.00` vs `1,250.00` matches as `number` and `2024-06-28` vs `28/06/2024` matches as `date`.
- **`--document <document_id>` on `run_eval` (repeatable, additive).** Restricts a run to named dataset items; absent, the run covers the whole dataset exactly as before. Matched exactly first, then as a unique substring — an **ambiguous or unmatched selector is refused before any submit** (a filtered run that measured nothing would exit 0 and read as a pass). Filtering happens *after* the full golden set is fetched, drift-checked and N28-validated, so a per-document run cannot skip a validation the full run performs; `golden_version` is still hashed over the **whole** item list (INV-04), so a filtered and a full run of the same golden set report the same version, and the quota ceiling counts the **selected** items, since that is what gets submitted.
- **Scorers and named classifiers (`--classifier`).** `classifier/scoring.py` is **the public authoring API** — import everything a custom scorer or gate needs from there (`ScoreContext`, `ScoreResult`, `Scorer`/`ClassifyFn`/`GateFn`, `compare_value`, `is_empty`); anything else under `classifier/` is harness and may change. `classifier/scorers.py` holds only the two shipped scorers, `classifier/canonical.py` the comparison engine, `classifier/gate.py` the fan-out, `classifier/registry.py` the name table. A **scorer** is one pure function over a single expected/actual pair returning one verdict literal — the same shape a platform custom scorer has, and 3 lines of body for each of the two shipped. A **classifier** is a scorer wrapped in the shared fan-out (`make_classifier`): which fields exist, prompts, pairing table rows by `match_key`, input validation, and the gate. Adding a comparison strategy is *write a scorer + one row in `CLASSIFIERS`* — nothing else is restated. A scorer receives a `ScoreContext` (a NamedTuple, so a later field breaks no existing scorer) carrying `name`, `kind` (`field`/`prompt`/`table_column`), `field_type`, `expected`, `actual`, **`confidence`**, `critical`, `format_critical`, `match_key` (table cells) and `source` (prompts). `confidence` is the notable unused one: it reaches every scorer and neither shipped classifier decides on it — a confidence floor is a ~3-line scorer (worked example in `scorers.py`, exercised in `tests/classifier/test_registry.py`). **A scorer can make one field fail the whole document**: return `ScoreResult(verdict, critical=True)` instead of a bare verdict and that field is gated whatever the golden says (on a table cell it escalates the block, since a row verdict carries no `critical` of its own). **Escalation only — the flags are OR-ed with the golden's, never replace them**: a scorer may make a field mandatory, never make a mandatory field optional, so "critical in the golden ⇒ gated" stays true and no scorer can quietly turn a real regression green. A rule about the document rather than a field (any `wrong_format` anywhere, a count of differences) belongs in the classifier row's **`gate`**, which `overall_gate` is only the default for.
- **The two shipped classifiers.** A run names a comparison strategy; it never imports one. `regression` (the default, and what every run without the flag gets) is the watched-Action behaviour, byte for byte. `pinned-file` differs in **one rule**: an empty expected value matched by an empty actual is a `match` rather than `missing` — agreement that neither version read anything — which is what lets a pinned golden mark every field critical while invented content still fails as `wrong_value`. Both share the comparison engine (canonicalization by `type`, table row pairing on `match_key`, input validation): measured before choosing, `gate.py` is 510 lines with 1,809 lines of tests behind it and the two cases differ in ~8, so forking would copy ~500 lines to change 8 and the copy would be the under-tested one. The flag is **private** — `classify`'s public signature stays the pinned two-argument contract (CT-02) and each registry entry is its own two-argument function. Adding a third is one row in `CLASSIFIERS`; `tests/classifier/test_registry.py` then holds it to the shared contract (two-argument signature, only the six verdict literals, a gate returning only PASS/FAIL) so a new entry cannot introduce a vocabulary the score names (INV-03) and the remediation UI do not know. **Registered names only, never an importable path from a flag** — that would make a CLI argument a code-execution surface on a runner holding IDP and platform credentials. An unknown name is a pre-run refusal (zero quota), never a silent fallback; the classifier used is logged on the pre-run line beside `golden_version`, though it does **not** yet reach `RunMetadata` on the platform.
- **Automation boundary — what a pipeline can and cannot do.** `golden_pipeline.py` automates every mechanical step and the mechanical half of reconciliation (`calibrate_golden.py`): `critical` from measured stability and corpus presence, one `match_key` and one `type` per field across the corpus. It cannot automate **whether the extractor's answers are right** — the only oracle is the document — so what it produces is an *agreement baseline*: a green run means the candidate agrees with the incumbent, never that either is correct. The pipeline prints that, and the gate's blind spots, at the end of every run rather than leaving it implicit. Sampling documents for a human read is still the step that turns the baseline into ground truth.
- **Model/version swap: the order is noise floor, then draft, then compare.** `scripts/noise_floor.py` establishes what the incumbent's disagreement with itself costs; `scripts/bootstrap_golden_set.py` then drafts a baseline from the incumbent over documents the customer already accepted; only then does a `run_eval` against a candidate version mean anything. Skipping the first step produces a golden set with the incumbent's coin-flips baked in as "expected", and a red build rate nobody can interpret. Both tools refuse to spend quota without `--yes`, print the exact extraction count first (`--plan`), and write owner-only (`0700`/`0600`) output that is gitignored — precisely: every FILE is `0600`, and a directory is `0700` when the tool creates it, but an existing directory you name as `--out`'s parent is left as it is (DEBT-99: tightening it chmodded your working directory or `$HOME`, and crashed on `/tmp` after the quota was spent). Directories the tools own outright (captures, extraction targets, the pin store) are still tightened — it carries the same sensitive extracted values as `.idp-regression-run-artifacts/`.
- **Why a console at all, and what stays on the platform (Epic E, user decision 2026-09-25).** The evaluation platform keeps the version-over-version regression view, the dataset/golden storage with server-enforced schema, and its own dashboards — none of that is rebuilt. The console exists for the three things the platform's data model structurally cannot hold: the **noise floor** (a corpus-level statistic measured against ONE version, with nothing to join it to a run), **calibration's blind spots** (the fields demoted out of `critical`, fail-open by design, so a green run cannot say what the gate is not looking at), and the **pin store's (action, version) axis** (dataset names are flat). **The floor never changes a gate** — `above`/`within` labels a red, it never clears one, and the exit code stays the gate's (INV-08). Platform history is read back read-only via `platform/insights.py`; nothing read there feeds a gate.
- **⚠️ THE CONSOLE SPENDS IDP QUOTA — on exactly one route (user decision, 2026-09-25, a deliberate reversal).** `POST /api/workflows/compare/start` runs `scripts/compare_versions.py` for real, so the primary use case works end to end from the browser. Everything else still prints the command. The `--yes` that used to be typed at a terminal is now **`approved_extractions`: the client must echo back the exact count this server computed from the REAL `--plan`, and a mismatch is a 409** — a stale page cannot approve a cost it never displayed. `tests/ui/test_api.py::TestQuotaBoundary` enumerates the route table and names the single quota-spending route, so widening it is a visible edit. The original reasoning against this (a loopback, unauthenticated port is a poor place for a button that bills a customer's org) was raised, overruled, and is recorded here rather than dropped.
- **The primary use case, end to end: "my corpus is valid at version X; I changed the LLM and published Y — is it still valid?"** In the UI: upload the ZIP (validated, nothing written), name the org/action/dataset, pick the two versions, `Plan` (spends nothing, prints the real 2N cost), then `Run — spend N`. It executes `compare_versions.py`, which unpacks **once** so the bytes compared are provably the bytes pinned, pins every document at the trusted version and verifies every one at the candidate. The job streams its output, is cancellable (**cancelling refunds nothing already extracted**, and the UI says so), and its verdict distinguishes `CHANGED` (a real regression — the gate working, a non-zero exit) from `RUN FAILED` (the batch broke).
- **The console has ONE workspace, and jobs run in it (defect fix, 2026-09-25).** Every tool here names its output relatively (`.idp-regression-pins/`, `.idp-regression-run-artifacts/`, …), i.e. relative to the *process's* working directory. The job runner used to launch `compare_versions.py` with `cwd=<repo root>` while the reader resolved paths against the *console's* cwd — so a validation started from a console running anywhere else wrote its pins and its run artifact where the Pins and Runs pages never look: **a paid-for batch that produced nothing visible, with no error**. `ui/workspace.py` is now the single answer; `--workspace` overrides it, and it defaults to the directory the console was started in. Credentials are decoupled from it on purpose — the console loads `.env` into its own environment at startup (workspace first, then repo root) and children inherit it, so the workspace can be any directory and the job still authenticates.
- **A job's result is the RUN ARTIFACT, never scraped text.** `STILL VALID` / `CHANGED` are **banner lines printed once per script**, not per document — the first implementation counted them and reported "changed: 1" for a forty-document run every time. `jobs.summarize()` now resolves the run artifact (by the `experiment=<run-name>-<run_id[:8]>` prefix on `run_eval`'s pre-run line, else the newest artifact written *after the job started*) and reports per-document verdicts through the authoritative `overall_gate`, plus a `run_id` the UI links to. **No artifact means no counts, never zero counts** — "nothing changed" and "we could not tell" are different answers and only one of them means the corpus is still valid.
- **Preflight before you pay (`GET /api/preflight`).** Whether this machine can run a validation at all, asked before an upload is priced. It **imports** `REQUIRED_ENV_VARS` from `idp_regression.adapter` and `idp_regression.platform` rather than re-typing the names, so a rename there cannot leave a trusted check passing on a machine that cannot run. Presence by **name only, never a value** (INV-02: this port is unauthenticated). Missing platform credentials are reported as loudly as missing IDP ones, because that combination is the expensive failure — the run reaches IDP, spends quota on every document, and only then fails.
- **Interpreting the verdict: the noise floor is a step of this workflow (T8).** Pin/verify compares **one** reading at the trusted version against **one** at the candidate, so if either version is nondeterministic a `CHANGED` cannot be told from the extractor disagreeing with itself — and a model swap is exactly when that is most likely. The wizard's step 4 runs `scripts/noise_floor.py` on a sample (`POST /api/workflows/floor/{plan,start}`), **defaulting to the TRUSTED version**: a field it flips on is one whose pinned value was a coin toss, so every later verdict on it is noise. That is the documented order (floor → draft → compare) and what `verify_document.py`'s own failure hint says to measure; the candidate is offered for the narrower "is *this* red reproducible". The finished job then links to `#/runs/<id>?baseline=<report>` so the run opens already read against the floor. **INV-08 is unchanged: the floor explains a red, it never clears one** — a workflow that measured a floor and reported "green after all" would be the silently-wrong GREEN build `## Rigor` names as this system's worst failure.
- **TWO routes spend IDP quota, and `/api/health` names both.** `POST /api/workflows/compare/start` and `POST /api/workflows/floor/start`. Both require `approved_extractions` echoed from a real `--plan`, and both are refused server-side when the preflight says this machine cannot finish a run. `tests/ui/test_api.py::TestQuotaBoundary` enumerates the route table AND asserts `/api/health`'s declaration equals it, so the spend set and what the console tells an operator about it cannot drift — they did once, when the floor was added and health kept claiming one route, with a green test cementing the denial.
- **One quota-spending job per workspace, and jobs outlive the console.** A `flock` on `<workspace>/.idp-regression-jobs.lock` admits one at a time: two batches against the same pin store interleave badly, since `pin_document` writes goldens on a deterministic id and `verify_document` reads them back — the `launchd` path has used `/usr/bin/lockf` for this since it existed. `flock` rather than a lock *file* so a crashed console cannot leave the workspace permanently unusable. Finished jobs are recorded under `.idp-regression-jobs/` **without their output** (that carries extracted values and already lives in the run artifact); a job still running when a console stopped is shown as **INTERRUPTED and never resumed** — the extractions it spent are spent either way.
- **The flags the UI can reach.** `--max-documents` (the script's own default is 200; a larger corpus used to fail *after* being uploaded and priced), `--glob`, `--repin`, and `--allow-partial`. The last stays **off by default and that default is load-bearing**: files that failed to pin have no golden, so verifying would skip them silently and exit 0 on the rest — "every pinned file is still valid" would be true and useless.
- **Action versions cannot be listed, only probed.** IDP has no enumeration endpoint (ADR-0006 §A′), so the UI's version picker sweeps a small semver grid with existence probes: each is one HTTP call and **spends zero extraction quota**. It reports `exists` and `unknown` but never renders `unknown` as absent, and it says when the sweep was truncated or rate-limited rather than presenting a partial list as complete. Probing is a **convenience, not a gate**: with no IDP credentials, a rate limit, or a non-semver scheme, the versions can be typed by hand.

- **Custom scorers are wired into the CLI (2026-09-25).** `orchestration/cli.py` calls `register_custom_classifiers()` **before the parser is built** — argparse freezes `--classifier`'s `choices` at construction time, so a spec registered later would be rejected before `registry.resolve()` ever saw it. A broken spec file is reported (`custom_scorer_not_loaded`) and skipped, never fatal to a run that does not name it; naming the broken one is refused, with a line pointing at the load failure rather than argparse's misleading "invalid choice". The selected spec is logged as `custom_scorer_selected name=… base=… spec_digest=…` — **run identity**, the same job `golden_version` does for the golden set (INV-04), because a spec file can be edited between two runs that both name `--classifier my-rule` and nothing else would say they compared differently. The digest covers `base` + `rules` only, so re-wording a description does not look like a comparison change.
- **Custom scorers are DATA, not code (`.idp-regression-scorers/`).** `registry.py`'s rule — *registered names only, never an importable path from a flag* — binds harder on a web form than on a CLI argument, so a UI-authored scorer is a closed-vocabulary JSON spec of `when → then` rules that compiles to an ordinary `Scorer`. No `eval`, no import path, nothing in a spec can name a Python object. It is also **monotone by construction and proved so per spec before saving and again on every load** (a hand-edited spec file that fails the proof is reported as `custom_scorer_not_loaded`, never registered — S-01.1 re-stamp #2 G-1): an action may set `critical`/`format_critical` only to *true*, and may produce only a verdict the gate fails on (`missing` or `wrong_value`). A spec can turn a match into a failure; it can never turn a failure into anything the gate passes. (Corrected 2026-09-27: the rule used to be "may not produce `match`", and `new_field`/`new_line`/`new_table`/`wrong_format` are also passes, so a spec could rewrite a real `wrong_value` into one and turn the gate GREEN; `verify_monotone` now compares gate outcomes; and since `wrong_value` fails only when `critical` while `wrong_format` fails when `format_critical`, `compile_spec` itself refuses any rewrite that would pass a field its base failed, whatever route the spec took) — so the worst an unaudited spec can do is fail a build that would otherwise have passed, never the silently-wrong GREEN build `## Rigor` calls this system's worst failure. A "this mismatch is acceptable" rule is deliberately not expressible. Specs carry rules and no extracted values, so unlike every other directory these tools write **this one is meant to be committed** — that is what makes a custom gate reviewable. `register_custom_classifiers()` is an explicit call, never an import side effect: a run that did not ask for custom scorers behaves exactly as before.
- **`.idp-regression-uploads/` holds the customer's FILES**, not just values extracted from them — the one thing `## Domain` says never leaves the machine. Owner-only (`0700`/`0600`) and gitignored. Validation (`--plan`-equivalent) writes nothing; unpacking is a separate, explicit act, and neither spends quota.
- **`IDP_REGRESSION_LOG_LEVEL`** — sets the CLI/watcher's log level (default `INFO`; e.g. `IDP_REGRESSION_LOG_LEVEL=DEBUG` for verbose output). Read directly by `orchestration/cli.py` and `orchestration/watch.py`, not `.env`-only — export it in the shell or set it in `.env` and `source` it as usual.

## Architecture

Four packages under `src/idp_regression/`, one seam each. The dependency direction is adapter → classifier → platform, with orchestration on top; nothing flows back.

- **`adapter/`** — the IDP boundary. OAuth token cache, urllib transport (no-redirect opener, so a 3xx can never re-send the Bearer token), submit + poll loop against a configurable terminal-status allowlist, and `normalize()` mapping IDP's volatile `pages[]` into the stable `NormalizedOutput`. Every failure is a typed error from `errors.py`; **no raw exception may escape `normalize()` or `extract()`**, and no extracted value, token or path appears in a message, log or `__cause__` chain.
- **`classifier/`** — pure. `classify()` + `overall_gate()` over the six verdicts. No I/O and no adapter/platform imports (INV-02, enforced by a test). This suite is the CI gate.
- **`platform/`** — Langfuse. The `PlatformAdapter` Protocol is `get_dataset` / `record_run` / `mark_run_status`; `insights.py` is the separate **read** seam (`PlatformInsights`) the console's dashboards use — a different Protocol on purpose, so a dashboard that cannot load can never stop a run. **Record-after (ADR-0005 #9):** the orchestrator computes every gate first and writes nothing during its loop; then one `record_run` replays the stored results through the SDK's `run_experiment` and attaches scores to the trace ids it returns. The Langfuse SDK import is confined to `make_platform()` (NFR N24).
- **`orchestration/`** — the `run_eval` facade and CLI (S-01.4, in progress). `load_dotenv()` runs before any SDK client is constructed (INV-05). The action id and version are **per-run CLI parameters, never env config**; `--version` is required with no fallback.
- **`ui/`** — Epic E's local console, on top of orchestration; nothing depends on it. `reader.py` reads run artifacts, floor reports, calibration reports and the pin store; `uploads.py` is the ZIP trust boundary; `jobs.py` runs the one quota-spending workflow as a cancellable **subprocess** (argv as a list, every value validated against `^[A-Za-z0-9._-]{1,128}$`, never a shell string); `api.py` is the HTTP surface and `server.py` the loopback-only entry point. The spec compiler lives in `classifier/custom.py` (pure, INV-02) and its file I/O in `orchestration/scorer_store.py`, so the direction stays classifier ← orchestration ← ui and the CLI can register a spec without importing the UI. Every reach into `scripts/` goes through `scripts_bridge.py` — one seam, so the floor comparison, the zip checks and the pin layout are **the real script called in process, never a reimplementation** (`golden_pipeline.py`'s rule). The React app is in `frontend/`, built to `frontend/dist/` and served by the same process.

Where the "why" lives: `docs/adr/` (0002 adapter · 0003 classifier · 0004 orchestration and failure containment · 0005 platform), `docs/design/{CONTRACTS,INVARIANTS,DATA-MODEL-01}.md`, per-story stamps and audits in `docs/qa/`, and running state in `docs/state/` (`PROGRESS.md` is the source of truth for what happened and why; also `HANDOFFS.md`, `DEBT.md`, `REGRESSIONS.md`).

## Langfuse facts that bite

Established live against 4.38.0 OSS in `events_only` mode; re-verify before a version bump.

- Every score needs **exactly one** target (`traceId` / `sessionId` / `datasetRunId`) plus an explicit `dataType`, or the write is a 400. Scores are idempotent on a client-supplied `uuid5` id.
- A run appears in the UI **only** when created via the SDK's `run_experiment`. REST `dataset-run-items` alone stores the link but surfaces nothing. **Corrected 2026-09-23:** this does *not* mean a run is verifiable via a runs-list API — this deployment's v4 `events_only` mode has none. `GET /api/public/datasets/{name}/runs` **404s**, body explicit: "not available in events_only mode". What actually works, confirmed live against two real runs today: poll `GET /api/public/v3/scores` filtered by score name and a recent timestamp — every score this codebase writes is `record_run`'s own upload, so a bounded, filtered poll (never read-after-write, per the next bullet) is how a run's landing is confirmed, not the Experiments tab or any runs-list endpoint.
- `GET /v2/scores` is gone — use `/v3/scores`, filtered by `id`. Public reads lag, so poll with a bound and never read-after-write.
- `GET /api/public/v2/datasets/{name}` does **not** return items; fetch them from the paginated `/api/public/dataset-items`. Getting this wrong yields a silently empty golden set that passes vacuously.
- The committed golden schema (`src/idp_regression/platform/schema/golden_schema_v1.json`) must satisfy Ajv `strict: true`: every `if`/`then` declares a `type`, every `required` key is in `properties`, and the minified schema stays under 10,000 characters (CT-05).
