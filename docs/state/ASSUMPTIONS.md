# Assumptions & open questions — the gaps the spec was built on

Feliz records every gap she filled with a guess at `/discover` (a *provisional* risk). The **architect confirms the gating risk** at `/design` — only an architect-confirmed **High + open** assumption is a Definition-of-Ready gap that blocks a story; Med/Low are advisory. Risk answers "if this is false, what breaks?": **High** = the feature's core behavior is wrong; **Med** = a secondary/edge flow; **Low** = cosmetic or trivially reversible. Resolve a High by a human confirm/refute (a refuted one corrects the UC/AC/examples — the wrong thing caught cheap) or a `/spike`. "No gaps — the ask was fully specified" is a valid, explicit entry. The gate is **off in the `prototype` rigor profile** (register kept as a note, nothing blocks).

| ASM-06 | **Post-UC-01 / trigger model** | **A new IDP action version's execution can be observed — by this app or by something it can subscribe to — so that regression validation fires automatically once a new prompt has run at IDP, rather than only when a human or a PR starts it.** ⚠️ **UNVERIFIED and currently REFUTED-BY-ABSENCE in the shipped design.** User requirement, 2026-09-21: *"We need to find a way to trigger the validation after a new prompt completes its execution at IDP."* **What is verified today:** the system is entirely **pull-based and externally triggered** — `run_eval` is started by a human or by CI on a prompt-change PR, then pulls the golden set from Langfuse, pulls extractions from IDP (`submit` → `poll` until terminal), classifies in-process and pushes one run record back. A grep across `docs/adr/` and `docs/design/` (2026-09-21) found **zero** webhooks, events, subscriptions or push mechanisms. **Consequence the sponsor should hear stated plainly: the safety net only catches prompt changes that go through a PR.** A version published and executed directly in Anypoint is invisible to this tool. **What already exists, and is half of any solution:** every run records `action_version` into `RunMetadata` (INV-04), so *"what did we last certify?"* is already answerable from Langfuse. The missing half is *"what is published / what just ran?"*, which requires an Anypoint API **this app has never called** — the only endpoint it knows is `POST /organizations/{org}/actions/{id}/versions/{v}/executions` on `idp-rt.{region}`, the **runtime** plane; listing/notification is a management-plane concern whose existence and shape are **unverified, and were deliberately not guessed at**. **Investigation carded as T-01.6.6** (discovery only, +1 pt, inside S-01.6's existing live-access window — it adds questions, not work): (1) is there a management API that lists an action's versions, and what does it return; (2) does submitting support a floating/`latest` version *(if so, detection is nearly free — submit one document, read back which version answered, compare to the last certified `action_version`)*; (3) does a published version carry a timestamp or monotonic ordering. ⚠️ **Cost asymmetry that decides the design:** a listing call is one cheap metadata request, while a regression run costs **N document extractions** of real IDP quota — so "just run it nightly" detects with the expensive instrument what a metadata call would catch cheaply, *unless* listing does not exist, in which case a low-frequency scheduled run may be the only option. The three answers decide between **cheap metadata watcher** / **scheduled full run** / **not feasible — stay with CI-on-PR**. ⚠️ **Scope fence:** anything built on the answers is **Epic-level, not MVP**; the IDP action id is already the only critical path and this must not become a second one. ⚠️ **Ambiguity still to be resolved by the user before design:** *"after a new prompt completes its execution"* — **(a)** a new action **version** was published and run, so re-run the golden set against it *(this product; the watcher serves it)*, or **(b)** a **production document** was extracted and we want to judge that output live *(**not** this product — there is no golden for an arbitrary production document, so the classifier has nothing to compare against; that is drift/confidence monitoring, a different Epic with a different data model)*. | **High** — it is the difference between a gate that catches every prompt change and one that catches only PR-routed changes | **open — investigation carded (T-01.6.6), nothing built** | User requirement 2026-09-21; recorded by the orchestrator after verifying the absence of any push mechanism in the design |
