# ADR-0002: IDP adapter & normalize() contract

**Status:** Proposed
**Date:** 2026-09-17
**Context (use case):** UC-01 (Run a baseline regression over a golden set)
**Risk:** High — the normalized-output contract is what the classifier, the run history, and (later) the remediation UI consume. Changing it after runs are scored on the platform invalidates historical `field:<name>` score semantics. **Atchim review: APPROVED (top-level gate, 2026-09-18 — opus; reviewer-independent, all five axes PASS).**

## Context

The IDP adapter is the only component that knows IDP's HTTP shape. Three calls (`docs/init/requirements-spec.md` Layer 1):
1. **Auth** — OAuth2 client credentials, `POST .../accounts/api/v2/oauth2/token`.
2. **Submit** — `POST {base}/organizations/{org}/actions/{action}/versions/{version}/executions` with the document as a file upload → execution `id`. Base host is region-specific.
3. **Poll** — `GET {base}/.../executions/{id}` until status is terminal → extraction body.

Confirmed from a live response sample (UC-01 Hand-off, 2026-09-17): the raw execution response is nested under `pages[]`, each page carrying:
- `fields` — `<name>.value` (and a per-value `confidence` in fuller examples).
- `tables` — a keyed map of arrays of row-objects: `tables.<table>[].<column>.value`.
- `prompts` — `prompt`, `source`, `answer.value`.

`normalize()` must walk into `pages[].fields.<name>.value` (and `pages[].tables.<table>[].<col>.value`, `pages[].prompts[].answer.value`) — **not** a flat top-level map.

Constraints that shape the adapter:
- **Action and version are per-run parameters** (BR1; amended 2026-09-19) — `action_id` and `version` are passed to `extract()` on every call, never hard-coded and never read from env inside the adapter. The version is the regression variable; the action is per-run so one environment can exercise several actions (Epic F routing). Both are validated at the CLI boundary before they reach the URL path: `action_id` must be a UUID, `version` must match `^[A-Za-z0-9._-]{1,64}$` — anything else exits non-zero before any IDP call (path-injection guard).
- **Terminal status is a configurable allowlist** (ASM-01, BR9) — read from config/env, never `== "SUCCEEDED"`. `SUCCEEDED` is confirmed real; the full enum (whether `PARTIAL_SUCCESS` exists in this org / appears in callbacks) is unconfirmed and is pinned by a `/spike` against the live org before implementation.
- **OAuth token cached for the run** (BR7) — one token at run start, reused across all documents; refreshed only on expiry within the run.
- **Per-document timeout, abort the run on timeout or hard failure** (ASM-02, BR10, AC5) — no partial runs.
- **All credentials from env/secrets** (BR6) — `IDP_CLIENT_ID`, `IDP_CLIENT_SECRET`, `IDP_REGION`, `IDP_ORG_ID`. Run parameters (`action_id`, `version`) are not environment config; `IDP_ACTION_ID` survives only as an optional CLI default (ADR-0004), and there is no env var for the version.
- **Confidence is kept available to the classifier but is NOT part of the golden-set comparison** (UC-01 Hand-off) — it flows through `normalize()` into the verdict/score so the remediation UI can use it, but the gate ignores it.
- **Shape variance across actions** (ASM-04) — the confirmed shape is from invoice/field-report actions; `normalize()` must not assume one fixed shape across all document types. For UC-01 (single baseline action) this is Low risk; it becomes Med for Epic F routing.

## Threat model

Trust boundary: **IDP** (external OAuth-authenticated HTTP service). IDP is a trusted *internal* service, but its output is still untrusted input to us — the adapter must not pass raw IDP JSON straight to the classifier or platform without normalization.

- **Spoofing:** OAuth client credentials mitigate; fail-closed on auth failure (A3) — never fall back to anonymous.
- **Tampering:** TLS to IDP; the execution `id` is opaque to us. Mitigation: we treat the polled body as data, never execute it. A hallucinated/malformed field name from IDP is a tampering-shaped input — mitigated by field-name sanitization at the `normalize()` boundary (see § Normalized-output contract / Field-name sanitization).
- **Information disclosure:** IDP credentials (client secret) are the sensitive surface. Mitigation: env/secrets only (BR6); token cached in memory, never logged; redact `Authorization` headers in any debug/observability output. `normalize()` uses structured (non-f-string) logging so a golden/actual value containing `\n` or `"` cannot break a log line or inject a fake telemetry field.
- **Denial of service:** IDP rate limits unknown (NFR). Mitigation: sequential-only at MVP (no concurrent submissions); per-document timeout; bounded retry for transient errors only, immediate abort on hard failure (Containment section in ADR-0004).
- **Repudiation:** the adapter returns the IDP execution status alongside the normalized output so the orchestrator records it in run metadata.

## Options considered

### Option A — Adapter returns the raw `pages[]` body; classifier walks pages
**Pros:** less adapter code.
**Cons:** pushes IDP's shape into the classifier, breaking classifier purity (ADR-0003) and coupling the pure logic to a volatile external contract. Shape variance (ASM-04) would leak into the classifier.

### Option B — Adapter `normalize()` flattens `pages[]` into the internal contract; classifier stays pure
**Pros:** the classifier depends only on the stable internal contract; IDP shape changes are absorbed in one place. Matches the seed (`design-inputs.md` ADR-2: classifier is pure and platform-agnostic) and UC-01 step 3d.
**Cons:** the normalized-output contract is now load-bearing — changing it is a cross-feature break (score semantics, remediation UI). This is the reversal cost; it's real but manageable with contract tests.

## Decision

We choose **Option B**. `normalize()` is the single seam between IDP's volatile shape and the stable internal contract. The adapter owns: OAuth token handling, polling with timeout, the configurable terminal-status allowlist, and `normalize()`.

### Adapter interface (contract-first)

```python
class IDPAdapter(Protocol):
    def extract(self, document_path: str, action_id: str, version: str) -> NormalizedOutput: ...
```

`extract()` is the only public method. It:
1. Ensures a cached OAuth token (fetch at first call, refresh on expiry).
2. POSTs the document to `actions/{action_id}/versions/{version}/executions` → execution `id`.
3. Polls until status ∈ `IDP_TERMINAL_STATUSES` (configurable allowlist) or timeout.
4. On terminal success: `normalize()` the raw body → `NormalizedOutput`.
5. On timeout / hard failure: raise (the orchestrator aborts the run — ADR-0004).

### Normalized-output contract (the internal shape `normalize()` emits)

```python
class NormalizedOutput(TypedDict):
    status: str                                   # the IDP terminal status string (e.g. "SUCCEEDED")
    fields: dict[str, FieldValue]                 # name -> {value, confidence}
    tables: dict[str, list[dict[str, FieldValue]]]  # table_name -> [{col_name -> FieldValue}]
    prompts: dict[str, PromptValue]               # prompt key -> {answer, confidence, source}

class FieldValue(TypedDict):
    value: str | None
    confidence: float | None                       # kept available; NOT part of golden comparison

> **Amended 2026-09-19 (QA S-01.2 F-3, typing only).** In code, the adapter's TypedDicts mirror the classifier's (`src/idp_regression/classifier/types.py`) so that `NormalizedOutput` is assignable to `classify()` under mypy (CT-01 key-parity test). They mark `tables`, `prompts`, `FieldValue.confidence`, `PromptValue.confidence` and `PromptValue.source` as `NotRequired`. At runtime `normalize()` always emits every key: the contract above describes the emitted shape, and `NotRequired` only marks keys a *consumer* must tolerate as absent.

# A row is a dict keyed by column name (NOT a TypedDict with wildcard keys —
# TypedDict cannot express `column_name -> FieldValue` for arbitrary columns,
# and `dict[str, list[Row]]` would not be mypy-typeable. A plain
# dict[str, FieldValue] per row is the expressible, mypy-checkable form.)
# A contract test mypy-checks these types.

class PromptValue(TypedDict):
    answer: str | None
    confidence: float | None
    source: str | None
```

Merge semantics across `pages[]`:
- `fields`: later pages win on name collision (last-wins); single field-name namespace across the document. (`pages[].fields.<name>.value` → `fields[<name>].value`.)
- `tables`: concatenate rows across pages per table name (`pages[].tables.<table>[]` → `tables[<table>] + [...]`).
- `prompts`: keyed by `prompt` string. **Key collision rule:** if two prompt entries share the same `prompt` string, `normalize()` raises `MalformedIDPOutputError` (duplicate-prompt) rather than silently dropping one — last-wins would hide a real IDP duplication bug. The Curator-visible prompt key is the `prompt` string; uniqueness is asserted at the trust boundary. (If a future action emits legitimately duplicate `prompt` strings with different `source`s, re-open this with an index-qualified key — out of scope for UC-01.)
  - *Amendment 2026-09-19 (ADR-0005 F10, R4):* the prompt key is the IDP `prompt` string **verbatim** (no trimming or case-folding): 1–200 chars, no control characters (`^[^\u0000-\u001F\u007F]{1,200}$`), matching the golden schema's `propertyNames` (CT-05). A prompt that violates this raises `MalformedIDPOutputError(reason="unsafe_prompt_key")`. The `[A-Za-z0-9_\-]` charset below does **not** apply to prompt keys.
- Confidence is preserved wherever the raw response carries it; absent confidence → `None`. The classifier and gate **ignore** confidence. **Amended 2026-09-19 (DEBT-18 option B, user decision):** confidence is never written to the platform, and the score comment is always `None`. Any remediation-UI use of confidence must come from the local run, not from Langfuse.

### Field-name sanitization at the trust boundary
Field names from IDP become platform score keys `field:<name>` (INV-03, BR11). An LLM-hallucinated field name containing `:`, a newline, or the literal `gate` would break score-key parsing downstream (INV-03). `normalize()` therefore **validates field names at the boundary** against a safe charset `[A-Za-z0-9_\-]` (and a non-empty length cap). A field name that fails this check is not silently dropped and is not passed through — it maps to a typed `MalformedIDPOutputError(field="…", reason="unsafe_field_name")` (the orchestrator aborts the run — ADR-0004). This is part of the untrusted-input contract (see §Threat model). A contract test feeds a malicious field name (`"total\ngate"`, `"a:b"`) and asserts the typed error. The same charset applies to `tables` keys. *(Amended 2026-09-19, ADR-0005 F10: previously also `prompts` keys; prompt keys now follow the verbatim rule above. A prompt-derived score name never uses the raw prompt: it uses a charset-safe derived id, `prompt:<first 16 hex chars of sha256(UTF-8 prompt key)>`, with the verbatim prompt in the score comment (INV-03). **Amended 2026-09-19 (DEBT-18 option B):** score comments are `None`. The verbatim prompt is golden content and never leaves the dataset item; the score name alone identifies the prompt. The exact score-name family is pinned by CT-03 in S-01.3.)*

### Mapping to the golden (consumed by ADR-0003)
- `golden.fields` (name → `{value, type, critical}`) compares against `actual.fields[name].value`.
- `golden.tables[<table>]` (with `match_key`, `critical`, `rows`) compares against `actual.tables[<table>]` by `match_key`. Each actual row is a `dict[str, FieldValue]` keyed by column name (post-revision ADR-0002 shape); the seed's top-level `line_items` block is normalised to `tables.line_items` in the golden schema (DATA-MODEL-01) so golden and actual share one keyed-map shape.
- `golden.prompts` (if present) compares against `actual.prompts[key].answer`.

### Configurable terminal-status allowlist (ASM-01 directive)
- `IDP_TERMINAL_STATUSES` read from env/config as a comma-separated list (e.g. `"SUCCEEDED,PARTIAL_SUCCESS,FAILED"`). Default: `["SUCCEEDED"]` only — fail-closed until a `/spike` pins the live-org enum.
- The "terminal success" set (statuses that should produce a `NormalizedOutput` rather than abort) is a separate, smaller allowlist: `IDP_SUCCESS_STATUSES` (default `["SUCCEEDED"]`). A status in `IDP_TERMINAL_STATUSES` but not in `IDP_SUCCESS_STATUSES` is a hard failure → orchestrator aborts (ADR-0004).
- Never `== "SUCCEEDED"` in code. Both allowlists are config; the spike pins the values.

## Design patterns

- **Adapter (GoF)** — `IDPAdapter` Protocol with one concrete implementation talking to IDP. Idiomatic: a `Protocol` + `MuleSoftIDPAdapter` class; `extract()` is the seam. The classifier never imports the adapter.
- **Strategy (injectable function)** — `normalize()` is a pure function `normalize(raw: dict, success_statuses: set[str]) -> NormalizedOutput`, injectable for testing with sample raw bodies. Idiomatic: a module-level function, not a class.
- **Repository (light)** — token caching is a small in-memory cache scoped to the run, held as a `TokenCache` **instance** on the adapter (not a module-level `_token` global). A module global is awkward for test isolation and any future concurrency; an instance is idiomatic, injectable in tests, and scoped to the adapter's lifetime. The Repository intent (a thin persistence facade over the token endpoint) fits; the form is a small class with `get()`/`refresh()`, not a module global.

## API contract (observable behaviors — Hyrum's Law)

What we commit to, that consumers may come to depend on:
- `extract()` returns a `NormalizedOutput` whose `fields` keys are exactly the field names IDP extracted for that document; `tables` keys are exactly the table names IDP returned. Adding a field to the IDP action does **not** remove existing keys (this is what makes `new_field` detection stable).
- `confidence` is always present as a key (possibly `None`); consumers may assume the field exists on every `FieldValue`.
- `status` is the raw IDP status string, passed through unchanged — consumers may assume it's one of `IDP_SUCCESS_STATUSES` when `extract()` returns rather than raising.
- `extract()` raises on timeout / hard failure / auth failure — it never returns a partial or "empty success" result. Consumers may assume a returned `NormalizedOutput` means a successful extraction.
- `normalize()` raises `MalformedIDPOutputError` on any malformed input (no `KeyError`/`AttributeError` escapes): schema validation at the boundary (top-level dict with either a top-level `fields`/`tables`/`prompts` container — the real wire shape — or a `pages` list; **(2026-09-23 correction, D1 terminal rule, supersedes R-1's "one wins" wording below) both are UNIONED when present, never mutually exclusive — a non-empty `pages` list contributes its entries AND a present top-level `fields`/`tables`/`prompts` container contributes the raw body as one more logical page; neither present → raises `reason="missing_envelope"`**; a present-but-non-list `pages` always raises `reason="invalid_pages"` outright, never falls through; each page dict with `fields`/`tables`/`prompts` or absent; every `FieldValue` is `{value: str|None, confidence: float|None}` after coercion); field/table/prompt names validated against `[A-Za-z0-9_\-]`; duplicate `prompt` strings raise; **(A11, supersedes the original text) a present confidence value outside its scale's valid range, NaN, non-numeric, or overflowing `float()` → raises `reason="invalid_confidence"`, NOT `None` and NOT clamped** — an ABSENT confidence key is still `None` (three-state preserved); the real `confidenceScore` key (0–100) is converted to 0–1, the legacy `confidence` key (0–1) passes through; **(M-1) a `confidenceScore` strictly between 0 and 1 → raises `reason="confidence_scale_ambiguous"`** rather than being silently rescaled; **(M-2) both confidence keys present on one cell → raises `reason="conflicting_confidence_keys"`**, regardless of either value's individual validity; bounded sizes (field value > 64 KB → typed error `value_too_large`; `tables.<t>` > 10_000 rows → typed error `table_too_large`). Consumers may assume a returned `NormalizedOutput` is well-formed and bounded. **A well-formed envelope whose recognised container(s) are genuinely empty is NOT an error** (R-1 empty-extraction decision) — it returns an empty `NormalizedOutput`; only the *absence* of every recognisable container raises.
- `extract()` and `normalize()` use structured (non-f-string) logging — a value containing `\n` or `"` cannot break a log line or inject a fake telemetry field (NFR N5/N19).

Versioning strategy: the `NormalizedOutput` TypedDict is versioned by Python type; shape changes require a new ADR. The `field:<name>` / `gate` score keys built on top of this contract are immutable (BR11).

## Consequences

- **Positive:** the classifier stays pure (ADR-0003) — it depends on `NormalizedOutput`, never on IDP. Shape variance across actions (ASM-04) is isolated to `normalize()`. Confidence flows to the remediation UI without touching the gate.
- **Negative:** the `NormalizedOutput` shape is now load-bearing. Changing it after runs are scored on the platform redefines historical `field:<name>` score semantics.
- **Follow-up work:**
  - `/spike` to pin `IDP_TERMINAL_STATUSES` and `IDP_SUCCESS_STATUSES` against the live org before implementation (ASM-01).
  - Contract tests for `normalize()` against captured raw IDP bodies (the spike should capture fixtures), including: malformed-body cases (typed errors, no raw exception escapes), a malicious field name (`"total\ngate"`, `"a:b"`) asserting the sanitization error, a duplicate `prompt` string asserting the collision error, a >64KB field value, a >10_000-row table, an invalid-confidence (NaN / 1.5) value asserting `None` (not clamp), and a three-state missing/empty/null case. A mypy contract test that type-checks `NormalizedOutput` / `FieldValue` / `PromptValue` / the `tables` dict-of-list-of-dict shape.
  - Register IDP credential set with Mestre (already listed in `## External services` as missing).

## Reversal cost

**High** and rising. Before the first run is scored on the platform: medium (rewrite `normalize()` + classifier together). After runs are scored: high — historical scores become ambiguous. Mitigation: the contract is small and the contract tests pin it; the risk is in *delaying* a needed change, not in *making* one. Locked once we score real runs.

Atchim review: APPROVED (top-level gate, 2026-09-18 — opus; reviewer-independent, all five axes PASS). Non-blocking debt: the IDP terminal-status / timeout / retry spike (ASM-01) must still pin `IDP_TERMINAL_STATUSES` / `IDP_SUCCESS_STATUSES` and the timeout value against the live org before S-01.2/S-01.4 implementation — this approval covers the contract structure, not the pinned values.

## Amendment 2026-09-22 — Poll contract: `?valueOnly=false` required, poll-interval floor raised to 10s (architecture-adherence review)

Raised by a user architecture-adherence review of `src/idp_regression/adapter/idp_client.py`, independent of the `/spike` in the §Follow-up work list (still open, still pins `IDP_TERMINAL_STATUSES`/`IDP_SUCCESS_STATUSES`/the timeout against the live org — this amendment does not discharge it). Two defects, both in the poll contract this ADR defines at §Decision step 3.

**A9. The poll GET must request the full cell shape — `?valueOnly=false`.**

**The rule.** §Context confirms the raw execution response nests every cell as `{"value": ..., "confidence": ...}`, and §Normalized-output contract commits `normalize()` to requiring that shape (`FieldValue.value` is not optional; a cell without a `"value"` key raises `MalformedIDPOutputError(reason="invalid_cell")`). What was undocumented: the Anypoint IDP execution-result endpoint returns **value-only** cells (a bare scalar, not the `{value, confidence}` mapping) **by default**, and the full shape is opt-in via a `?valueOnly=false` query parameter on the result GET. The adapter's poll GET carried no query string, so against the live API every extraction would have failed `normalize()`'s own boundary check (or, had `normalize()` been laxer, silently dropped confidence) — a live fail-shut defect masked entirely by synthetic fixtures that were hand-written in the full shape.

**Evidence.** `_poll()` built `f"{base_url}/{execution_id}"` with no query string (idp_client.py, pre-fix). `normalize()` (`adapter/normalize.py:92-94`) already raised on a missing `"value"` key — the two pieces of code disagreed about what the wire actually returns, and nothing in the test suite exercised the real query string because every fixture and fake already supplied the full shape.

**Fix.** The poll GET — the one whose body `_poll()` returns as the extraction result — now requests `f"{base_url}/{execution_id}?{urlencode({'valueOnly': 'false'})}"`. Not the submit POST (submit returns only an execution id, no cell data). Built via `urllib.parse.urlencode`, not string concatenation, so a second query parameter can be added later without re-deriving the escaping. Pinned by a literal-URL test (a mutant dropping the query string goes RED) and a `normalize()`-level test proving a value-only cell (`{"total": "1150.00"}`) is rejected as malformed — the defect's live consequence, made visible in the suite rather than only in a comment.

**Reversal cost.** Low — a single query-string change at one call site, covered by a URL-pinning test that will catch a regression immediately.

**A10. Poll-interval floor raised from 3.0s (unstated default) to a required minimum of 10.0s.**

**The rule.** `DEFAULT_POLL_INTERVAL_SECONDS` was `3.0`, with no floor below the general `> 0` timing check — a caller (or a future config change) could set it arbitrarily low. §Threat model's Denial-of-service line ("IDP rate limits unknown … bounded retry for transient errors only") already commits to IDP-side rate protection; a 3s poll against a long-running extraction is roughly 40 requests per document, which is the opposite of that posture. `MIN_POLL_INTERVAL_SECONDS = 10.0` is now enforced in `_validate_timing` at construction — same typed `IDPConfigurationError` shape as the existing `MAX_*` bounds (QA F-1 precedent), fail-closed, never discovered mid-poll. `DEFAULT_POLL_INTERVAL_SECONDS` is raised to `10.0` to match.

**Evidence.** No incident — this is a hardening ahead of the live-org `/spike` (§Follow-up work), which still has to pin IDP's actual rate limits. 10.0s is a conservative floor chosen to bound worst-case request volume, not a measured value; it is deliberately loose enough to revisit once the spike has real numbers.

**Consequence for `DEFAULT_POLL_TIMEOUT_SECONDS` (`120.0`, unchanged).** At the new default interval this is 12 polls per document — still a sane number; not changed by this amendment, and no reason found to change it.

**Reversal cost.** Low while unreleased — a single constant plus a validation floor, both covered by boundary tests (9.999 rejected, 10.0 accepted). Raising the floor further later is free; lowering it below 10.0 after this amendment ships would need a stated reason (e.g. the `/spike`'s pinned live-org rate limit turns out to tolerate less), not just convenience.

## Amendment 2026-09-22 — A11: the real wire envelope has no `pages[]`, and `normalize()` was fail-open against it (REG-11)

Raised by the top-level orchestrator while closing signoff blocker B-5, from the **first live extraction ever run** (`seed-001-clean.pdf`, action `078ca317-d3a2-4979-8386-7daf4453ea3e` v1.0.0) — not by a test. The captured body is committed verbatim at `tests/fixtures/live/seed-001-clean.raw.json` (commit `0c82a02`) and is now the primary wire contract; every fixture predating it was hand-authored in the shape `normalize()` wanted, not the shape IDP returns.

**The real shape.** Top-level keys `documentName`, `fields`, `id`, `status`, `tables` — **no `pages` key at all**. `fields` is a flat `name -> {value, confidenceScore, geometry}` mapping (nine fields observed); `tables` is `table_name -> [row, ...]`, each row `column -> {value, confidenceScore, geometry}` (one table, `line_items`, two rows observed). `confidenceScore` is on a **0–100 scale** (observed 95.0–99.0) — not `confidence` on 0–1 as every prior fixture assumed.

**D1 — the envelope was fail-open (the regression, REG-11).** `normalize.py` did `pages = raw.get("pages", [])`. Against the real body this silently defaults to `[]`, the merge loop never runs, and `normalize()` returned `NormalizedOutput(status="SUCCEEDED", fields={}, tables={}, prompts={})` **without raising** — a genuine nine-field, two-row extraction became an empty one wearing a success status. Exactly the "silently-wrong GREEN build" `CLAUDE.md ## Rigor` names as the worst failure this system can produce, and not caught by 886 tests because every fixture agreed with the code, never with the API.

**D1 fix — envelope decision.** `normalize()` now accepts the top-level `fields`/`tables` container as the **primary** shape (treating the raw body itself as a single logical page). `pages[]` is kept as an **optional, still-supported secondary** shape — never observed live, but not removed, since only a one-page document has ever been seen and a genuine multi-page response might still use it (an explicitly flagged, still-unverified unknown, not a decision to drop support). **Whichever shape is present wins** (`pages` takes precedence if both happen to appear); **if neither `pages` nor a top-level `fields`/`tables` key is present, `normalize()` now raises `MalformedIDPOutputError(reason="missing_envelope")`** — this is the regression pin. Killed by `test_response_with_neither_pages_nor_top_level_container_raises_typed_error` and `test_response_with_neither_container_does_not_return_an_empty_success` (`tests/adapter/test_normalize.py`), and mutation-verified: reverting the raise to the old `raw.get("pages", [])` default fails 21 tests, including the exact REG-11 pins and the live-capture positive suite.

⚠️ **CORRECTED 2026-09-22 (independent review, REQUEST CHANGES round, R-1) — "whichever shape is present wins" was PRESENCE-based and reopened the exact fail-open class this amendment exists to close, through its own new rule.** `has_pages = "pages" in raw` is `True` for a present-but-EMPTY `pages: []`, so a genuine top-level extraction sitting beside an empty `pages` key was silently discarded — reproduced live: `{"status":"SUCCEEDED","pages":[],"fields":{...nine real fields...}}` returned `fields={}` with **no raise**. The docstring's sentence *"a response with neither present must raise, never silently return an empty success"* was **factually wrong**: an empty `pages` list is neither absent-`pages` nor a present-and-populated one, and the code returned empty for it anyway.

**Fix — precedence is now CONTENT-based, not presence-based:**
- a **non-empty** `pages` list wins outright, regardless of any top-level container beside it (unchanged from the original intent, just now correctly gated on content);
- an **empty or absent** `pages` falls through to the top-level `fields`/`tables` container;
- neither a non-empty `pages` nor a top-level container is present → raises `missing_envelope`, exactly as before, but now correctly reached when `pages: []` is the only thing present too;
- a **non-list** `pages` value (e.g. a string) always raises `invalid_pages` outright and never falls through — falling through there would hide a genuinely corrupt response shape rather than an absent/empty one.

**Empty-extraction decision (explicit, per R-1's request).** A well-formed envelope whose recognised container(s) are genuinely *empty* (`{"fields": {}, "tables": {}}`, or a `pages` entry that is itself an empty dict) is **accepted** and returns an empty `NormalizedOutput` — presence of the key is read as "IDP looked and found nothing", which is a legitimate extraction outcome, not a malformed response. Only the *absence* of every recognisable container raises `missing_envelope` — "we don't recognise this response at all" is the only case rejected. This preserves the pre-existing, unchanged test `test_normalize_defaults_missing_blocks_to_empty` (`pages: [{}]` → empty, no raise) and is pinned symmetrically by two new tests: `test_empty_pages_list_does_not_outrank_a_populated_top_level_container` (the R-1 regression itself — recovers all nine fields and the table from a `pages: []` + populated top-level body) and `test_well_formed_envelope_with_genuinely_empty_containers_is_not_an_error` (`{"fields": {}, "tables": {}}` → empty, no raise, by decision). ## Correction 2026-09-23 — A11 D1 terminal rule (third occurrence of the class) + D2 prompts envelope

Two further defects found by adversarial probing after `6075cce` (the R-1 content-based-precedence commit), reproduced directly, not alleged.

**D1 — the R-1 fix was still incomplete: a non-empty but BARREN `pages` still discarded a populated top-level container.** R-1 changed precedence from presence-based (`"pages" in raw`) to content-based (`raw_pages` truthy), so `pages: []` no longer outranked a real top-level shape. But "truthy" only tested that the **list** was non-empty, not that it **yielded** anything: `pages: [{}]` (or `[{}, {}]`) is a non-empty list whose sole content is empty dicts, and it still won outright over a top-level container carrying nine real fields and a table — the nine fields silently vanished with no raise. A pages list carrying one unrelated field (`{"fields": {"zzz": ...}}`) beside a top-level container carrying nine real ones showed the same defect one notch less extreme: the real fields never even entered the result.

**This is the third occurrence of the same defect class, one level deeper each round:**
1. Original A11 fix: `pages` **absent** silently defaulted to `[]` (`raw.get("pages", [])`), the merge loop never ran, and `normalize()` returned an empty success — the original REG-11 finding.
2. R-1 fix: `pages: []` (present-but-empty) still outranked a populated top-level container, via presence-only (`"pages" in raw`).
3. This fix: `pages: [{}]` / `[{}, {}]` (present, non-empty as a **list**, barren as **content**) still outranked a populated top-level container, via content-tested-as-list-length rather than content-tested-as-yield.

Each prior round fixed the immediately-reported shape by testing emptiness one level further **in** (key presence -> list length) without ever making the test terminal, because the underlying model in every round was still **"exactly one envelope wins, and the loser is fully discarded."** Any such model has an infinite regress of "how do we know THIS instance of the winning envelope is really empty" — a list can be non-empty in a way that's still barren; a barren-looking page can itself be non-empty one level further in; the regress does not have a natural floor.

**The terminal fix removes the "one wins" model entirely.** `normalize()` no longer selects between `pages[]` and the top-level container — it **unions every recognised container that is present**: each `pages[]` entry (when the list is non-empty) *and* the top-level body itself (when it carries `fields`/`tables`/`prompts`) are all appended to the same `logical_pages` list and walked by the one merge loop that already combines multiple `pages[]` entries with last-wins/concatenate semantics. **Why this ends the family and a fourth variant cannot appear:** presence is now tested exactly **once**, at the top, per container (`pages` non-empty? top-level container present?) — never re-tested against the container's *content* to decide inclusion. An empty or barren container, however deeply nested its emptiness, simply contributes zero entries to the merge once included; it is never in competition with anything else for the privilege of being the sole source. There is no "is this content sufficient" question left to answer wrong one level deeper, because that question is no longer asked at all.

**The empty-extraction decision (R-1) is preserved unchanged.** A recognised container that is present but genuinely empty (`{"fields": {}, "tables": {}}`, or a `pages` entry that is itself `{}`) still counts as present and still contributes nothing — "IDP looked and found nothing" remains a legitimate result. What changed is only that a present-but-empty container never again gets to *suppress* a different, populated container sitting beside it — because nothing is suppressed by anything under a union rule. `missing_envelope` is raised in exactly one case, unchanged: no non-empty `pages` list **and** no top-level `fields`/`tables`/`prompts` key at all.

Pinned by `tests/adapter/test_normalize.py::test_barren_or_junk_pages_never_discards_a_populated_top_level_container`, parametrized over `pages: []`, `pages: [{}]`, `pages: [{}, {}]`, and a `pages` list carrying an unrelated field beside a populated top level — all four assert the top-level content survives intact. `test_a_response_with_a_pages_key_and_top_level_fields_merges_both_not_exclusive` replaces the now-incorrect `..._ignores_any_top_level_fields_or_tables` (which asserted the opposite — a decoy top-level field must NOT appear — that assertion described the exact defect this fix removes). Mutation-verified (hand-revert, confirm RED, byte-identical restore verified by `shasum`): (1) removing the union and reverting to R-1's mutually-exclusive `if pages: ... elif top-level: ...` selection fails all four parametrized barren/junk cases plus the merge test; (2) dropping the top-level-container append entirely fails 28 tests across the suite, confirming the append is genuinely load-bearing and not incidental.

**D2 — a prompts-only response raised `missing_envelope` (fail-shut, and plausibly a real action shape).** The envelope check recognised `fields` and `tables` but not `prompts`, so an action returning only prompt answers and no extracted fields was rejected outright, even though `NormalizedOutput.prompts` is a first-class member and `docs/state/DEBT.md` DEBT-69 already records the `prompts` shape as unverified against the live API (this action emits none). **Fix:** `prompts` now counts as a recognised top-level envelope container on equal footing with `fields`/`tables` — `has_top_level_container` is `"fields" in raw or "tables" in raw or "prompts" in raw`. This does not weaken D1's rule: it is one more container the union rule includes when present, nothing more. Pinned by `test_top_level_prompts_only_is_a_recognised_envelope_not_missing`; mutation-verified by dropping the `"prompts" in raw` disjunct and confirming that test alone goes RED.

⚠️ **The `prompts` shape itself remains unverified against a live IDP response (SR-1, DEBT-69).** This fix makes the envelope *check* consistent with the type `NormalizedOutput` already declares — it does not verify the wire shape a prompt-only response would actually carry. SR-1 binds: a wire-contract assumption is only "verified" against a **captured live response**, never a fixture authored from the parser, and no such capture exists for `prompts`. This fix must not be described, here or elsewhere, as if it closed that verification gap — it does not.

**Reversal cost.** Low — the union replaces a five-line if/elif/else with an equivalent-shaped list-building block; nothing downstream depends on which container a given entry came from, since the merge loop already treats every logical page identically regardless of source.

## Correction 2026-09-22 — A9/A10 were optimistic in three specific ways (independent review, S-3)

Same A9/A10 style as above: the existing text is **kept**, not silently rewritten. Raised by an independent review of the `2026-09-22 architecture-adherence review` amendment above, not by a defect in the shipped behavior — all three points are about what A9/A10 *claim*, not what the code *does*.

**(1) A10's "12 polls per document" is a ceiling, not a typical count.** Each poll iteration is *GET latency + a full `self._poll_interval_seconds` sleep* (`idp_client.py` `_poll()`'s success path sleeps the whole interval, not interval-minus-latency), so "12 polls" is only reached if every GET is instantaneous. At a more realistic 2s GET it is closer to ~10 polls before the 120s budget is spent; at 5s GET, ~8. Not wrong, just tighter in practice than "12" suggests on its own.

**(2) A10 silently tripled the per-GET socket timeout — undocumented until now.** `per_call_timeout = min(self._poll_interval_seconds * 2, remaining) or remaining` (`idp_client.py:426`) ties the per-GET transport timeout to `poll_interval_seconds`. Raising the default interval 3.0 → 10.0 therefore also raised the per-GET socket timeout from 6s to 20s — a real behavioral change neither A10's text nor the amendment's commit message mentioned. Probably a net improvement (a slow IDP response is less likely to be killed mid-flight), but it was a side effect of a floor-hardening change, not a decision made on its own merits, and it should have been named at the time.

**(3) A10's stated threat is not reachable through the factory today.** `make_idp_adapter()` (`idp_client.py:487-561`) passes `submit_timeout_seconds`, `poll_timeout_seconds`, `token_refresh_margin_seconds` and `poll_retry_max_attempts` from env, but **never `poll_interval_seconds`** — there is no `IDP_POLL_INTERVAL_SECONDS` env var. Every production adapter therefore gets the `DEFAULT_POLL_INTERVAL_SECONDS = 10.0` default unconditionally, and `MIN_POLL_INTERVAL_SECONDS` can only ever fire on a direct `MuleSoftIDPAdapter(...)` constructor call (i.e. from a test). A10's framing — "a caller (or **a future config change**) could set it arbitrarily low" — states a threat that is not live through any production path that exists today. The floor is legitimate **future-proofing** for whenever such an env var is added, not a control that is actively constraining anything in production right now. (Whether to add `IDP_POLL_INTERVAL_SECONDS` is a separate, open design question — out of scope for this correction; it is not decided here.)

**(4) `?valueOnly=false` is now vendor-confirmed, not just inferred.** A9's evidence was internal (the wire capture disagreeing with `normalize()`'s expectations). MuleSoft's own IDP API docs independently confirm the same requirement: ["add the `valueOnly=false` query parameter to your GET request"](https://docs.mulesoft.com/idp/automate-document-processing-with-the-idp-api) on the execution-results GET. This closes what were previously two unverifiable-against-vendor-docs items in A9 to a documented one.

**Reversal cost.** None of the above changes any code or test — this is a correction to what A9/A10 claim, not a new decision. If (3) motivates adding `IDP_POLL_INTERVAL_SECONDS`, that is a new, separately-decided amendment.

Reviewer: independent review that raised this correction is the review itself (2026-09-22); not yet re-reviewed by Atchim.

## Correction 2026-09-23 — R-1/R-2: the D1 union's collision precedence, pinned and reconciled (REQUEST CHANGES on `6489560`)

An independent review of the D1 terminal-rule commit judged the union itself genuinely terminal for the old discard family (it tried to falsify it and could not) but found the union opened a **new**, unpinned family: what happens when the same field/table row/prompt key appears in **both** a `pages[]` entry and the top-level rollup. Two Required findings, both fixed here.

**R-1 — collision precedence was emergent and unpinned (surviving mutant).** `normalize()` appends `raw` (the top-level rollup) to `logical_pages` **after** any `pages[]` entries, and `_merge_fields` is last-wins — so the top-level body silently wins any shared field name. That was already true of the code; it was simply never asserted. **Verified surviving mutant:** swapping the two `logical_pages` append blocks (top-level first, `pages[]` second) left the then-current suite (944 passed / 15 skipped) fully green — proof the suite exercised the union but never a genuine collision. **Fix:** `test_top_level_field_wins_over_a_colliding_pages_entry` (`tests/adapter/test_normalize.py`) pins the top-level-wins precedence explicitly; mutation-verified by re-running the same swap (hand-revert, confirm RED, byte-identical restore verified by `shasum`) — the new test alone (plus, incidentally, the new prompt-override test below, since prompt precedence in the current code is tied to loop position too) goes RED.

**R-2 — three unreconciled collision policies across a seam not designed for this.** The merge semantics (`_merge_fields` last-wins, `_merge_tables` concatenate-no-dedup, `_merge_prompts` raise-on-duplicate) were chosen for **page-vs-page** merging; the D1 union reuses them verbatim for **page-vs-top-level**, where the realistic trigger is a genuine multi-page body carrying a top-level **rollup** alongside `pages[]` — a common API shape, and the one shape that produces both containers at once. Reconciled as follows, one decision per container:

- **`fields`** — last-wins, top level silently wins (R-1, above). Kept as-is; this is the seam's baseline behavior every other decision below is measured against.
- **`tables`** — **decision: no change, dedup NOT added.** Rows concatenate across the seam with no dedup, so a row genuinely present in both a `pages[]` entry and the top-level rollup **doubles** in `NormalizedOutput.tables`. This is deliberately left alone: deduplicating would require a `match_key` per table, and `match_key` is **golden-schema** knowledge (`docs/design/DATA-MODEL-01.md`) supplied only at classify time — `normalize()` is a pure boundary function with no golden-set input and has no principled key to dedup rows by. Any dedup attempt here would be a guess (e.g. dedup by full-row equality), not a rule, and would risk silently dropping two rows that are genuinely distinct but happen to coerce identically. **What is now written down, not fixed:** `classifier/gate.py`'s row-pairing (`compare_rows`, indexing actual rows by normalized `match_key`, ~lines 213-226) is what collapses this duplication in practice at gate time — the gate's masking of this is **load-bearing** for the tables seam and was previously undocumented. Anything reading `NormalizedOutput` directly instead of going through the gate (ADR-0007's local run artifact, Epic E's future remediation UI) still sees every doubled row twice; that residual is not addressed by this correction. Pinned by `test_top_level_table_row_concatenates_without_dedup_across_the_seam`.
- **`prompts`** — **decision: `duplicate_prompt` is no longer fatal across the pages/top-level seam; it stays fatal within a single container.** The reviewer's argument, accepted: raising for a key appearing in both a `pages[]` entry and the top-level rollup applies a **page-vs-page integrity rule** (two independent entries genuinely claiming the same answer is always a defect) to a **rollup echo** (the same answer reported at two levels of one wire shape) — the identical situation `fields` already tolerates silently via last-wins. Making `prompts` the one container that hard-fails the whole extraction for this is inconsistent with how the other two containers treat the same overlap. **Fix:** `_merge_prompts` gained an `allow_override: bool` parameter, `True` only for the single top-level-rollup pass (`normalize()` identifies it via `page is raw`); a prompt key already seen in an earlier `pages[]` entry is then overridden last-wins instead of raising, matching `fields`. A **true** duplicate within one container — two entries in the *same* `pages[]` entry, or two entries in the top-level rollup's own `prompts` list — still raises `duplicate_prompt` exactly as before; this is tracked separately (`seen_in_this_list`) from the cross-container check (`seen_keys`), so the relaxation is scoped to the seam only. Pinned by `test_top_level_prompt_wins_over_a_colliding_pages_entry_instead_of_raising` (the relaxation) and `test_duplicate_prompt_within_the_top_level_rollup_itself_still_raises` (the boundary — a within-container duplicate is unaffected); the pre-existing `test_duplicate_prompt_string_raises_typed_error` (two entries in one `pages[]` entry) is unchanged and still passes.

**What remains unverified (SR-1, DEBT-69 — unchanged, not closed by this fix).** All three seed PDFs are single-page (`/Count=1` confirmed in each); no available document produces a `pages[]`-plus-top-level-rollup body, so **whether a real multi-page MuleSoft IDP response ever carries both containers at once is still an open, unverified question** — this correction fixes the inconsistency **on its merits** (consistency with `fields`'s existing precedent, not empirical confirmation of the trigger) and must not be described as having settled that question. Settling it needs a genuinely multi-page document, which nobody has produced yet.

**Reversal cost.** Low for all three — each is a local decision inside `_merge_fields`/`_merge_tables`/`_merge_prompts` / the loop that calls them; nothing downstream depends on which container a colliding key or row came from, and reverting any one decision does not require touching the other two.
